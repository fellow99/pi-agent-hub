# 会话同步附属文件（图像与附件落盘转存）（`004-会话同步-附属文件.md`）

> 本文档设计 **hub 会话同步侧** 的附属文件（图片，以及今后 video/audio/pdf/artifact 等）落盘与引用
> 机制。解决现状：三环境（pi / opencode / dsh）会话同步后，聊天上下文里的图片因 `url` 恒为空，
> 前端只能渲染 `image: ` 占位标签，无法看到实际图片。
>
> 关联文档：协议与同步总则 [`001-协议规范.md`](./001-协议规范.md)；下发的交付图片中转见
> [`007-下发聊天消息.md`](./007-下发聊天消息.md)（那是「下发方向」，本文是「同步方向」，两者互补）。

| 项 | 值 |
|---|---|
| 方案 | **B：hub 同步落盘转存**（附件数据不内联进 transcript，落盘 + 只传 url 引用） |
| 落盘根目录 | `${dataDir}/sync/`（与既有 `${dataDir}/deliveries/` 平级） |
| 单文件路径 | `${dataDir}/sync/<host>/<agent>/<会话ID>/<hash>` |
| 内容寻址 | 文件名为附件内容 **sha256 hex**（64 位小写），同会话内自动去重 |
| 读取面 | 浏览器前端经 **/api/hub**（session cookie + GET 免 CSRF）读取 |
| 文档状态 | v0.1（2026-11-18）· 方案公示，实现前评审 |

## 0. 背景与问题

### 0.1 现状（真机取证 2026-11-18）

三环境同步回读后的 image block 均 `url: ""`，前端 BlockCard 只渲染 `<el-tag>image: {{ mime }}</el-tag>`：

| 环境 | 镜像 image-block 数 | 数据是否在本环节可得 |
|---|---|---|
| opencode v2 | 若干（增量 44→52 含 1 个） | ✅ 插件已把 `message.files[].data`（base64）作 `dataBase64` 上传 |
| pi（pi-web） | 7（会话含带图 user） | ⚠️ 会话文件 part 是 `{type:"image", data: base64, mimeType}`，镜像文件已含数据，**hub 组装时丢弃 `part.data`** |
| dsh | 2 | ❌ 会话里是 `attachmentId: sha256:<hash>` 引用，**插件读侧只传 mimeType、没读附件对象** |

底层共性：**hub 无同步侧附件转存**，`toTranscriptItem()` 组装 image block 时丢弃一切二进制，只留 `mime`。

> 补充取证：hub 镜像文件（`<dataDir>/agent/sessions/<proj>/<ts>_<hs>.jsonl`）里 image part **已含**
> base64 数据（iVBORw0… 可 grep 到），因此**存量会话的图片数据也在**，迁移可行。

### 0.2 方案取舍

| 项 | 方案 A（data-uri 内联） | 方案 B（hub 落盘转存，本文） |
|---|---|---|
| transcript 响应 | 每次全量带 base64（1MB 图 → 响应 +1.3MB；多图更明显） | 只带 url（几十字节） |
| 存储 | hub 数据库膨胀 | 文件系统落盘，内容寻址去重 |
| 缓存 | 无 | sha256 文件名天然可长缓存（ETag/Cache-Control） |
| 鉴权 | 无（data-uri 明文） | 受 hub 会话鉴权保护 |
| 改动量 | 小（hub 2 处 + 前端） | 中大（见 §10） |
| 复用/扩展 | 不适用 | 统一承载今后 video/audio/pdf/artifact 等附属文件 |

**决策**：采用方案 B。附图：`image`；通用附属文件：`attachment`（本文一并定义，承载今后类型）。

## 1. 术语

| 术语 | 含义 |
|---|---|
| **附件（attachment）** | 会话消息中携带的二进制文件：图片、将来的视频/音频/PDF/artifact 等 |
| **同步侧** | daemon → hub 的会话镜像同步（`POST /api/v1/sync/sessions/:id`），区别于下发 `deliver` |
| **hash（sha256）** | 附件内容 `sha256` 十六进制（64 位小写），内容寻址键 |
| **hubSessionId** | hub 会话主键（`hs_` + 26 位 base32），落盘路径三段中的「会话ID」用它 |

## 2. 总体设计

```
插件 read_session ──canonical entries（image/attachment part 内联 base64）──▶ daemon
   │
   └─ POST /api/v1/sync/sessions/:id（Bearer daemon token）
        │  hub-side SyncAttachmentStore：
        │   1) 逐条提取附件 part → 校验（mime/大小/数量）
        │   2) sha256 内容寻址落盘 dataDir/sync/<host>/<agent>/<会话ID>/<hash>
        │      存在即跳过（幂等/去重）
        │   3) part 改写为 { type:"image"|"attachment", mime, url }（db 只存引用，不存二进制）
        ▼
   hub db（镜像 entries 已脱敏：无内联二进制）        ──▶ console 读取
                                                     GET /api/hub/sessions/:hubId/attachments/:hash
                                                     （cookie 鉴权 + hash 白名单）→ <img>/<a> 渲染
```

**核心不变式**：
1. **二进制只出现一次**：插件 → hub 同步时传入 base64；落盘后 hub **不保留 base64**，镜像只存 url。
2. **内容寻址**：同一会话内相同内容只落盘一份（同名文件 = 同 hash）。
3. **读取走会话鉴权**：附件 URL 放在 `/api/hub` 命名空间下，浏览器凭 hub 登录 cookie 读取。
4. **杜绝路径穿越**：URL 中 hash 强制 `^[0-9a-f]{64}$`；且只服务「db 中某 block 已注册」的 hash。

## 3. 目录与文件布局

### 3.1 目录约定

```
${dataDir}/sync/
└── <host>/                    # hostId（token 配置映射，如 debian-opencode）
    └── <agent>/               # agent kind（opencode / pi / dsh …）
        └── <hubSessionId>/    # hs_xxx
            └── <sha256hex>    # 附件内容（无扩展名；mime 存于镜像 block / 响应头）
```

- `<host>`、`<agent>`：取自同步请求对应的 `SessionRow.host_id` / `agent_id`（落盘时已有上下文，见 §5.2）。
- `<hubSessionId>`：取当前同步的 hub 会话 id（`hs_xxx`）。
- `<sha256hex>`：内容哈希，天然去重；同一会话内同图多处出现共享同一文件。
- 不写 `manifest.ndjson`：镜像 block 的 `url` 本身就是注册表；GC 依据目录 mtime（见 §9.3）。

### 3.2 与既有目录的关系

| 目录 | 方向 | 内容 | 说明 |
|---|---|---|---|
| `${dataDir}/deliveries/<deliveryId>/images/<i>` | 下发 | deliver 附带图 | 007 已有，本文不动 |
| `${dataDir}/sync/<host>/<agent>/<hs>/<hash>` | 同步 | 会话镜像附属文件 | **本文新增** |

### 3.3 存储实现类

新增 `packages/hub-service/src/sync-attachment-store.ts`（职责对齐既有 `image-store.ts`）：

```ts
export interface SyncAttachmentInput { mime: string; dataBase64: string; name?: string }
export interface SyncAttachmentRef { mime: string; url: string; sha256: string; bytes: number }

class SyncAttachmentStore {
  constructor(dataDir: string)
  // 校验并落盘全部；任一项失败回滚本轮新增，抛 SyncAttachmentError（不污染镜像）。
  async save(host: string, agent: string, sessionId: string,
             parts: SyncAttachmentInput[]): Promise<SyncAttachmentRef[]>
  // 读取：校验 hash 格式 → 定位文件 → 返回 {mime, bytes, buffer}
  async read(host: string, agent: string, sessionId: string, hash: string): Promise<{mime: string; bytes: Buffer}>
}
```

校验阈值（初值，可配置；与 007 交付图片对齐）：

| 项 | 值 |
|---|---|
| 单附件大小上限 | 10 MB（`SYNC_ATTACHMENT_LIMITS.maxSingleBytes`） |
| 单条消息附件数上限 | 10（`maxCount`） |
| 单次同步附件总量上限 | 100 MB（`totalBytes`） |
| mime 白名单 | `image/*`、`video/*`、`audio/*`、`application/pdf`（今后按类型逐项扩充） |

> 越界附件**整体拒绝该批同步**（与 007 交付图「任一张不合法不落任何文件」一致），由 daemon 侧
> 可降级为「仅文本不附图」重试（插件策略见 §8，⬜ 待实现）。

## 4. 协议（canonical part）扩展

### 4.1 既有 image part：读入统一 + 落盘脱敏

当前三种形态（插件产出）：

| 插件 | 现有 part 形态 |
|---|---|
| opencode v2 | `{ type:"image", mimeType, dataBase64 }` ✅ |
| pi（pi-web） | `{ type:"image", data, mimeType }`（`data`=base64） |
| dsh | `{ type:"image", mimeType }`（**无数据**，需插件补 §8.3） |

**统一读入**（hub 端兼容）：`dataBase64 = part.dataBase64 ?? part.data`。pi 无需改插件。

**落盘后镜像形态**（hub 存储，脱敏）：

```jsonc
// 落盘前（插件→hub，canonical part，含内联数据）
{ "type": "image", "mimeType": "image/png", "dataBase64": "iVBORw0KGgoAAAA…" }
// 落盘后（hub 镜像内存储，只留引用）
{ "type": "image", "mimeType": "image/png",
  "url": "/api/hub/sessions/hs_xxxxxxxx/attachments/3f8e…（64 位 sha256）" }
```

### 4.2 新增通用 attachment part（承载今后类型）

```jsonc
{ "type": "attachment",
  "mimeType": "video/mp4",            // 或 image/png / application/pdf …
  "dataBase64": "…",
  "name": "clip.mp4",                 // 可选，展示/下载文件名
  "width": 1920, "height": 1080 }     // 可选（媒体 I/O 元数据）
```

落盘后同理改写为 `{ type:"attachment", mimeType, url, name }`。后续新类型（video/audio/pdf/artifact）
按本 part 追加，不新增「kind 家族」，hub/前端按 `mimeType` 分发渲染。

> ⚠️ 本文档 v0.1 落地范围 = **image** 端到端（三环境看到图）；`attachment` 通用 part 的协议面本文
> 先行定义，但 **video/audio/pdf 的插件适配与前端渲染按 8.4 / 7.2 标记 ⬜ 待后续迭代**。

## 5. hub 侧落盘流程

### 5.1 入口

同步写入唯一入口（与 001 §3 对应）：

```
POST /api/v1/sync/sessions/:id        ──已有的同步端点（Bearer token）
   └─ sessions.sync(row, request)     ──session-store，已有；本文在此前后接入附件落盘
```

### 5.2 落盘时机与上下文

在 `sessions.sync()` **写镜像前**执行（保证「镜像只存 url」不变式）：

1. 收集本批新增 entries 中全部 `image`（含内联数据）与 `attachment` part → `SyncAttachmentInput[]`。
2. `SyncAttachmentStore.save(host, agent, sessionId, inputs)`：
   - 逐条校验 → `sha256(dataBase64)` → `mkdir -p <dir>` → 临时文件写 `tmp-<pid>-<rand>` → `rename` 到
     `<dir>/<hash>`（若已存在则跳过）。
   - 全部成功后返回引用数组；任一条失败 → `rm -rf` 本轮 `<sessionId>` 目录中新增文件，抛错使本次同步失败
     （daemon 收到失败后可重试）。
3. 用返回的 ref 改写原 part（`dataBase64` 删除，`url` 写入）。同步签名/镜像写库流程不变。

> 上下文来源：`row.host_id`、`row.agent_id`、当前 `id`（hubSessionId）——`sessions.sync()` 已在签名中携带 `row`，无需改路由。

### 5.3 幂等与并发

- **幂等**：同内容同 hash：文件存在即跳过（不报错、不重写）。daemon 重复同步/重试安全。
- **并发**：同一会话并发写同 hash → `rename` 原子覆盖，内容一致无害。跨会话不同 hash 独立目录无冲突。
- **与 db 一致性**：db 写入在附件落盘成功后；若 db 失败（罕见），残留附件文件靠 GC 兜底（§9.3）。

## 6. 读取路由（hub → 前端）

### 6.1 端点

```
GET /api/hub/sessions/:hubId/attachments/:hash
```

- 挂在 **/api/hub** 命名空间：session cookie 鉴权 + **GET 免 CSRF**（复用 app.ts 既有中间件，§114–135）。
- 语义：读取 `dataDir/sync/<row.host_id>/<row.agent_id>/<hubId>/<hash>` 并返回。
- 响应头：`Content-Type: <mime>`、`Cache-Control: public, max-age=31536000, immutable`（sha256 内容寻址）、`Content-Length`、`ETag: "<hash>"`。

### 6.2 校验（安全）

1. `:hash` 必须匹配 `^[0-9a-f]{64}$`，否则 400。
2. `:hubId` 查会话 → 得 `host_id/agent_id`；会话不存在 → 404。
3. **注册表校验**：仅当该会话的某 block `url` 恰好等于请求 URL 时允许读取（防任意文件暴露）。
   实现：从镜像反查（读取时顺序扫描 block 或附加内存索引，量小可接受；⬜ 规模大再建索引）。
4. 文件缺失 → 404（客户端按缺失渲染占位）。

### 6.3 与既有静态/下载路由的关系

- transpcript 读镜像（§5 后已是纯净 url）→ 前端 `<img src>` 同源请求，带 cookie ✓。
- 不做代理/网关转发；不暴露 `/api/v1`（那是 daemon 域）。

## 8. 插件侧适配（三环境）

| 插件 | 现状 | 需要改动 |
|---|---|---|
| opencode v2 | image part 已带 `dataBase64` | **无需改**（§验证：files→dataBase64 已实现） |
| pi（pi-web） | part 带 `data`(base64) | **无需改**（hub 统一读 `dataBase64 ?? data`） |
| dsh | 只传 `mimeType`，未读附件 | **需改插件**（见 8.3） |

### 8.1 opencode v2（无改动）

`v2MessageParts()` 已产出 `{ type:"image", mimeType, dataBase64 }`，满足 hub 读入契约。

### 8.2 pi-web（无改动）

pi 会话文件 part `{ type:"image", data, mimeType }` 由 `readSessionFile` 原样入 hub；hub 读入统一
`dataBase64 ?? data` → 落盘。插件零改动。

### 8.3 dsh（需改插件）

dsh 会话（`.zstd`）里 image part 是引用：

```jsonc
{ "type": "image", "attachment": {
    "attachmentId": "sha256:35770bd…",
    "mediaType": "image/png", "bytes": 12966, "width": 800, "height": 800, "name": "logo_on_white.png" } }
```

附件对象存储在 `~/.dsh/attachments/v1/objects/<hash.slice(0,2)>/<hash>`（真机已确认路径）。

改动（`packages/sync-plugin-dsh/src/plugin.ts` readSession 读侧）：
1. 解析 `attachment.attachmentId`（`sha256:<hash>`）→ 定位对象文件。
2. 读取对象 → `base64` → 产出 `{ type:"image", mimeType: attachment.mediaType, dataBase64 }`（带 name/宽高可选）。
3. 读不到对象 → 降级为 `{ type:"image", mimeType }`（保持占位，不阻断同步）。

## 9. 边界、限制与运维

### 9.1 存量迁移（数据已在 hub）

- 现状：hub 镜像文件已存含 base64 的 image part（§0.1 取证）。
- **决策**：做一次性迁移（低成本）：遍历全部镜像 → 检测含数据的 image/attachment part → `SyncAttachmentStore.save` 落盘 → 改写 part 为 url 重写镜像文件。
- 触发：新增 `sync-attachment-store` 时附带 `migrateExistingMirrors(dataDir)`（启动/命令开关执行一次）。
- 迁移幂等：已是 url 形态的 part 跳过。

### 9.2 大小与滥用

- §3.3 阈值 enforced at save；超限整体拒绝，daemon 可降级重试（⬜）。
- mime 白名单：拒绝非常见/潜在危险类型（默认除白名单外拒绝）。

### 9.3 删除与 GC

- 会话删除（既有 delete 流程）→ 同步清理 `<dataDir>/sync/<host>/<agent>/<hs>` 目录（幂等 rmdir -force）。
- **孤儿清理**：目录 mtime 超过 N 天且不再被任何会话镜像注册 → 删除（⬜ 提供 `gcSyncAttachments` 工具，初版手动手工命令）。
- 不清除共享文件：同会话内 hash 共享由「会话目录内内容寻址」自然满足；跨会话不共享（隔离清晰）。

### 9.4 安全

| 威胁 | 对策 |
|---|---|
| 路径穿越（`../../`） | hash 格式白名单 `^[0-9a-f]{64}$`；目录段由 host/agent/hs 来自 row（不可从 URL 构造） |
| 未授权读取 | /api/hub cookie 鉴权 + block url 注册表校验（§6.2.3） |
| 超大文件耗尽磁盘 | saved 前校验单文件/总量上限 |
| 内容嗅探 | 响应强制 `Content-Type` 来自 mime（不从内容推断）；可为非 image 加 `X-Content-Type-Options: nosniff` |

## 12. 决策记录

| # | 决策 | 理由 |
|---|---|---|
| D1 | 落盘路径含 `<hubSessionId>`（非 nativeId、非全局 hash 池） | 用户指定；会话隔离清晰、GC 粒度好、避免跨会话耦合 |
| D2 | 落盘在 `sessions.sync()` 写镜像前（非读取时） | 保「镜像只存 url」不变式；读取零副作用、零重复落盘 |
| D3 | 读取走 `/api/hub`（cookie + 注册表校验）而非 `/api/v1`（Bearer） | 前端浏览器无 daemon token；同源 cookie 最自然 |
| D4 | 不做 manifest 索引，url 即注册表 | 内容寻址 + 镜像 block 引用已够；减少一套状态 |
| D5 | 存量迁移一次性做 | 图片数据已在 hub 镜像（取证），成本低、体验完整 |
| D6 | dsh 单独补插件 | 数据在本地 `.dsh/attachments` 对象库，只有插件能读到 |
| D7 | `attachment` 通用 part 先行定义、分类型迭代落地 | 为 future 类型（视频/PDF/artifact）定契约，但不阻塞本期 image 端到端 |

**待验证 ⬜**：dsh 附件对象读取在真机三种会话的覆盖率；附件量与 transcript 首屏峰值下的性能；GC 运行时策略。
