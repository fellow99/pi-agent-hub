# 工程目录同步（`005-工程目录同步.md`）

> 本文档定义 **hub-console 经 hub-service、sync-daemon 实时浏览主机真实工程目录与读取文件内容** 的
> 请求-应答链路（以下简称「工程目录同步」或 FS Bridge）。
>
> 关联文档：协议总规范见 [`001-协议规范.md`](./001-协议规范.md)；现有会话虚拟文件树（将被本能力取代的
> 会话推导视图）见 `specs/202-console-session-viewer/spec.md` §7。
>
> | 项 | 值 |
> |---|---|
> | 状态 | 已实现（2026-11-13，Docker + 本机 daemon + 真实浏览器联调通过） |
> | 通信模式 | **异步轮询**：console 发起 → hub 经 SSE 下发 → daemon REST 回传 → console 轮询取结果 |
> | 鉴权 | console 侧 Cookie+CSRF（仅 admin 可发起，GET 轮询不限角色）；daemon 侧 Bearer host token |
> | 能力边界 | 只读；单级目录懒加载；白名单严格约束可访问路径 |
> | 文档版本 | v0.2（2026-11-13） |
>
> **实现要点（与设计的落地差异）**
> 1. hub 侧 daemon 回传校验按结果双形状判别：list_dir 结果含 `entries`（无 `type`），read_file
>    结果含 `type`；公共必填字段为 `path`。校验逻辑独立在 `hub-service/src/fs-payload.ts`。
> 2. 前端 el-tree 采用**纯懒加载**：根级（level 0）也经 load 钩子拉取会话 cwd，不混合 `:data`，
>    否则懒加载模式下根数据被忽略恒显示 No Data；会话切换以 `treeKey` 重建树并中止在途请求。

## 1. 背景与目标

### 1.1 问题

202 会话查看器右栏的「文件树」是从会话工具调用（Read/Write/Edit/Bash）**推导的虚拟视图**，hub 本身不具备
主机文件系统访问权。实测（以 `D:\pi-workspace` 的会话 `hs_jhoym43j…` 为例，146 个路径）：

- Read/Write/Edit 结构化工具产生的 13 个路径全部准确；
- Bash 低置信正则提取产生 109 个噪音路径（中文 prose 片段、`/dev/null`、`$PATH`、shell 表达式残留等），
  导致文件树与真实目录严重对不上；
- 虚拟视图既不完整（未被工具触碰的文件不出现），也不反映文件当前是否存在。

### 1.2 目标

新增一条由主机上的 **sync-daemon 实际执行 `readdir`/`readFile`** 的数据链路，让 console 看到**主机真实
工程目录**，并能读取受限的文件内容。链路必须：

1. 复用现有 SSE 下发 + REST 回传骨架（与 `deliveries` 同构），不引入新通信范式；
2. 异步轮询，天然容忍 daemon 离线/重连，无长连接超时坑；
3. 双层白名单严格收敛可访问路径，杜绝任意路径遍历；
4. 全链路只读，不提供任何写/删/执行能力。

### 1.3 非目标

- 不做目录递归一次性拉取（仅单级懒加载）；
- 不做文件写入/修改/删除/上传；
- 不做目录变更监听（watch）与主动推送；
- 不替代会话镜像视图的历史取证用途（本期右栏切换为真实目录；镜像文件树接口保留不删，见 §10）。

## 2. 总体架构与数据链路

### 2.1 角色

| 角色 | 进程/位置 | 职责 |
|---|---|---|
| hub-console | 浏览器 SPA | 发起目录/文件请求、轮询结果、渲染树与查看器 |
| hub-service | 中心服务（Docker） | 鉴权、白名单第一道校验、SSE 下发、请求态机、结果暂存 |
| sync-daemon | 主机 Node 进程 | SSE 长连、白名单终校验、执行 `readdir`/`stat`/`readFile`、REST 回传 |

### 2.2 时序（异步轮询）

```
hub-console                hub-service                 sync-daemon(主机)
    |  POST /api/hub/fs-requests        |                          |
    |  {hostId, kind, path}             |                          |
    |---------------------------------->|                          |
    |  ① console 鉴权(admin+CSRF)        |                          |
    |  ② 会话 cwd 白名单校验(第一道)      |                          |
    |  ③ 建 requestId, state=dispatched  |                          |
    |  ④ sse.send(hostId,"fs_request",   |                          |
    |        {requestId,kind,path})      |                          |
    |     sse.send 失败(离线)->503       |  SSE event: fs_request   |
    |<----------------------------------|------------------------->|
    |  202 {requestId,state:"dispatched"}|  POST /api/v1/fs-requests/:id/ack
    |                                   |<-------------------------|
    |                                   |  state=accepted          |
    |                                   |  ⑤ daemon 白名单终校验    |
    |                                   |     readdir/readFile     |
    |  GET /api/hub/fs-requests/:id      |  POST /api/v1/fs-requests/:id/result
    |---------------------------------->|  {ok, result|error}      |
    |  {state:"accepted"|...} (继续轮询) |<-------------------------|
    |                                   |  state=completed|failed  |
    |  GET /api/hub/fs-requests/:id      |  结果内存暂存 5min        |
    |---------------------------------->|                          |
    |  200 {state:"completed", result}   |                          |
    |<----------------------------------|                          |
    |  渲染目录/文件内容                  |                          |
```

### 2.3 为什么是异步轮询而非同步等待

现有 `deliveries`（app.ts `POST /api/hub/deliveries` + SSE `deliver` + `/api/v1/deliveries/:id/ack|result`）
已验证此模式：hub 不挂起 HTTP 请求，daemon 离线/慢/重连都不会占用连接，状态可查询、可超时、可失败收敛。
目录浏览是「转圈→出内容」的交互，前端 1s 轮询体验足够。

## 3. 协议与接口契约

> 沿用 `001-协议规范.md` 的双轨：console 走 `/api/hub/*`（Cookie+CSRF），daemon 走 `/api/v1/*`（Bearer token）。

### 3.1 console → hub：发起请求

```
POST /api/hub/fs-requests
Content-Type: application/json
X-CSRF-Token: <csrf>
Cookie: hub_session=<session>

{
  "hostId": "laptop-win",
  "kind": "list_dir" | "read_file",
  "path": "D:\\pi-workspace\\pi-desktop-ark"
}
```

**响应（daemon 在线且已下发）：** `202 Accepted`
```json
{ "requestId": "fsr_<uuid>", "state": "dispatched" }
```

**前置校验与错误：**

| 情况 | 状态码 | error.code |
|---|---|---|
| 非 admin 角色（viewer） | 403 | `forbidden_role` |
| CSRF 失败 | 403 | `csrf_failed` |
| `hostId` 无对应 daemon token 配置 | 404 | `host_unknown` |
| `path` 非字符串/为空、`kind` 非法 | 400 | `invalid_request` |
| `path` 不在该 host 任一已知会话 cwd 之内（第一道白名单） | 403 | `path_not_allowed` |
| 该 host 当前无 SSE 连接（`sse.send` 返回 false） | 503 | `host_offline` |

### 3.2 console → hub：轮询结果

```
GET /api/hub/fs-requests/:requestId
```

| state | 含义 | HTTP 行为 |
|---|---|---|
| `dispatched` | 已下发，daemon 尚未 ack | 200 |
| `accepted` | daemon 已 ack，执行中 | 200 |
| `completed` | 成功，含 `result` | 200 |
| `failed` | 失败，含 `error` | 200（错误在体内，不用非 2xx，便于轮询统一处理） |
| `expired` | TTL 内未完成 | 200 |
| 未知/已清理的 requestId | — | 404 `not_found` |

**响应体：**
```json
{
  "requestId": "fsr_…",
  "state": "completed",
  "kind": "list_dir",
  "result": { /* 见 §3.5，kind 不同结构不同 */ },
  "error": { "code": "…", "message": "…" }
}
```

### 3.3 hub → daemon：SSE 下发

新 SSE 事件 `fs_request`（`SseHub.send(hostId, "fs_request", payload)`）：
```json
{
  "requestId": "fsr_…",
  "kind": "list_dir" | "read_file",
  "path": "D:\\pi-workspace\\pi-desktop-ark"
}
```
daemon 在 `handleEvent` 新增 `else if (event.event === "fs_request")` 分支，与 deliver/import/export 并列。

### 3.4 daemon → hub：ack 与 result（Bearer 鉴权）

```
POST /api/v1/fs-requests/:requestId/ack            -> 200 { ok: true }
POST /api/v1/fs-requests/:requestId/result
{
  "ok": true,
  "result": { /* §3.5 */ }
}
// 或失败：
{
  "ok": false,
  "error": { "code": "denied|not_found|…", "message": "…" }
}
```
hub 按 `requestId` 定位内存中的请求记录（校验该 token 对应的 host 与请求归属一致，防跨 host 冒写）。

### 3.5 结果数据结构

**list_dir（单级，仅直接子项）：**
```json
{
  "path": "D:\\pi-workspace\\pi-desktop-ark",
  "entries": [
    { "name": "entry", "isDir": true, "size": 0, "mtimeMs": 1792166132432 },
    { "name": "README.md", "isDir": false, "size": 12034, "mtimeMs": 1792166132000 }
  ],
  "truncated": false
}
```
- 目录在前、文件在后，各自按名称排序；`truncated` 表示子项数超过上限（见 §6）被截断。
- 不含递归内容；前端展开子目录时对该子路径再发一次 `list_dir`。

**read_file（按类别，§5）：**
```json
// 文本
{ "path": "…\\README.md", "type": "text", "content": "<utf8 原文>", "size": 12034 }
// 图片/视频/PDF：base64 data URL，前端直接喂 <img>/<video>/<iframe>
{ "path": "…\\logo.png", "type": "image", "mimeType": "image/png",
  "dataUrl": "data:image/png;base64,……", "size": 204800 }
```

## 4. 白名单与路径安全（核心）

### 4.1 两道防线

| 防线 | 位置 | 规则 |
|---|---|---|
| 第一道 | hub-service | 请求 path 必须落在该 host **已知会话 cwd 集合**之内，否则 403 `path_not_allowed`，不下发 |
| 第二道（终判） | sync-daemon | 按本机配置 `fsAllowedDirs` 判定，**daemon 拥有最终否决权** |

即使 hub 被绕过或数据不一致，daemon 仍独立拒绝越界请求。

### 4.2 daemon 配置 `fsAllowedDirs`

在 `SyncDaemonConfig` 新增（与既有 `agents.import.allowedRoots` 同风格）：

```ts
export interface SyncDaemonConfig {
  // …既有字段
  /** 工程目录同步允许访问的项目目录白名单；条目为具体项目目录，禁止盘根。 */
  fsAllowedDirs?: string[] | null;
}
```

`sync-daemon.json` 示例：
```json
{
  "host": { "name": "laptop-win" },
  "fsAllowedDirs": ["D:\\pi-workspace", "D:\\oh-workspace\\DevEcoStudioProjects\\app_jkh_launcher"]
}
```

**判定逻辑（daemon 端，先于任何 fs 调用）：**

```
normalize(p): 统一分隔符、path.resolve 折叠 .. 与符号、转小写比较（Windows 盘符不区分大小写）

if Array.isArray(fsAllowedDirs):
    if fsAllowedDirs.length === 0:
        -> 拒绝一切，error.code = "denied_all"          // [] 显式全禁
    allowed = fsAllowedDirs.map(normalize)
    校验：任一 allowed 为盘根（如 "D:\\"、"/"）-> 配置加载期报错，拒绝启动该能力
    if 存在 root 使 normalize(path) === root 或以 root + 分隔符 为前缀:
        -> 放行
    else:
        -> 拒绝，error.code = "denied"
else (null / undefined):
    回退第一道同源规则：path 属于该 host 已知项目目录才放行
    daemon 侧的「已知项目目录」来源：对各插件子进程调用 list_sessions（daemon 现有能力，
    见 daemon.ts syncAll 已取得每个 session 的 cwd）汇总去重得到 cwd 集合；
    为避免每次请求都触发子进程 RPC，MAY 缓存该集合并在每次同步周期刷新
    -> 不满足则 error.code = "denied"
```

### 4.3 路径规范化与越界防护

- 一律 `path.resolve` 处理 `.`/`..`，禁止以「字符串 includes」判断前缀（避免 `D:\pi-workspace-evil`
  误匹配 `D:\pi-workspace`），必须按路径段边界比较；
- 拒绝含 NUL（`\0`）的路径；
- 符号链接：默认 `readdir` 不跟随到白名单外（`readFile` 前对真实路径再做一次白名单判定，
  `fs.realpath` 后校验，防 symlink 逃逸）；
- 白名单条目本身在配置加载时 `realpath` 归一，比较双方都用真实路径。

## 5. 文件分类与限额

daemon 先 `stat` 取大小与类型，再决定是否读取与如何编码。

| 类别 | 扩展名白名单（小写匹配） | 大小上限 | 处理 |
|---|---|---|---|
| 文本 | `.ts .tsx .js .jsx .mjs .cjs .vue .json .json5 .md .txt .css .scss .html .xml .yaml .yml .ini .conf .sh .bat .ps1 .sql .csv .log .ets .ts` 去重 | **1 MB** | UTF-8 原文；解码失败按 `text_decode_failed` |
| 图片 | `.png .jpg .jpeg .gif .webp .svg .bmp .ico` | **10 MB** | base64 data URL + 对应 MIME |
| 视频 | `.mp4 .webm .mov .m4v` | **10 MB** | base64 data URL |
| PDF | `.pdf` | **10 MB** | base64 data URL（`application/pdf`） |
| 其它二进制 | 不在上述白名单 | — | **不读取**，`binary_unsupported` |

**超限与错误码：**

| 情况 | error.code |
|---|---|
| 路径不存在 | `not_found` |
| list_dir 目标不是目录 | `not_a_directory` |
| read_file 目标是目录 | `not_a_file` |
| 超出类别大小上限 | `file_too_large`（message 带实际/上限字节） |
| 不支持的二进制类型 | `binary_unsupported` |
| 白名单拒绝 | `denied` / `denied_all` |
| 其它 fs 异常 | `daemon_error`（message 带原始错误，不泄露敏感绝对路径以外信息） |

base64 膨胀约 4/3：10MB 文件 ≈ 13.3MB，低于现有 `express.json({limit:"128mb"})` 上限，无需调整。

## 6. hub-service 状态机与生命周期

### 6.1 状态机

```
            sse.send 成功                 ack 到达                 result(ok)
(创建) -----------------> dispatched ---------------> accepted -----------------> completed
   |                          |                        |   |
   | sse.send 失败            | TTL 60s 无 ack/result   |   | result(ok:false)
   v                          v                        v   v
503 host_offline（不建记录）  expired <-----------------  failed
```

- 状态枚举复用 `DeliveryState` 命名风格，新增 FS 请求专用集合：
  `dispatched | accepted | completed | failed | expired`；
- TTL：自建记录起 **60s** 未进入终态 → 惰性置 `expired`（轮询命中时判定，无需后台定时器）；
- 终态结果（completed/failed/expired）在内存保留 **5 分钟**供轮询，之后惰性删除；
- 纯内存 `Map<requestId, FsRequestRecord>`，hub 重启即失（请求类临时数据，可接受，前端按 `not_found` 重新发起）。

### 6.2 记录结构（内存）

```ts
interface FsRequestRecord {
  requestId: string;
  hostId: string;            // 绑定 host，result 回传校验 token 归属，防跨 host 冒写
  kind: "list_dir" | "read_file";
  path: string;
  state: FsRequestState;
  createdAt: number;
  acceptedAt?: number;
  finishedAt?: number;
  result?: unknown;
  error?: { code: string; message: string };
}
```

### 6.3 轮询节奏与前端超时

- console 轮询间隔 **1s**；
- 前端整体超时：list_dir **30s**、read_file **60s**；超时停止轮询并提示「主机响应超时」；
- 组件卸载/切换目录时取消轮询（AbortController + 清 timer），避免无效请求堆积。

## 7. 前端改造（hub-console）

### 7.1 API 客户端（`api.ts` 新增）

```ts
createFsRequest(hostId, kind, path): Promise<{ requestId: string }>
pollFsRequest(requestId): Promise<FsRequestRecord>
// 封装为便捷方法（内部完成 create + 轮询直到终态/超时）
listDir(hostId, path): Promise<DirListing>
readFile(hostId, path): Promise<FileContent>
```

### 7.2 右栏组件调整

- `FileTreePanel.vue`：数据源从「会话虚拟文件树（`/sessions/:id/files`）」切换为**真实目录**。
  - 根节点 = 当前会话 `cwd`（已知在白名单内）；首次进入自动 `listDir(cwd)`；
  - el-tree 懒加载：展开目录节点时对其 path 调 `listDir`，已加载目录缓存结果（组件内 LRU，沿用现有 30 项上限）；
  - 节点展示真实 `isDir/size/mtime`，去掉 `touchedBy` 工具标签（真实目录无此概念）；
  - hostId 取自当前会话的 `hostId`。
- 文件查看器：点击文件调 `readFile`，按 `type` 渲染：
  - text → `MdPreview`（markdown）或 `<pre>`（其它文本，沿用现有代码块样式）；
  - image → `<img :src="dataUrl">`；video → `<video controls>`；pdf → `<iframe :src="dataUrl">`；
  - 错误态（too_large/binary_unsupported/denied）用 el-empty/el-alert 明确提示。
- 权限：viewer 角色下右栏目录区显示「目录浏览需要管理员权限」空状态，不发起请求（admin-only，§8）。
- `SubagentPanel.vue` 不受影响，维持会话镜像数据。

### 7.3 与会话树的衔接

左栏选中会话后，其 `cwd` 与 `hostId` 直接作为右栏真实目录的根与目标主机，无需用户手输路径，
也保证请求起点天然落在白名单内。

## 8. 鉴权与权限矩阵

| 动作 | console admin | console viewer | daemon（Bearer） |
|---|---|---|---|
| 发起 fs-request（POST） | ✅ | ❌ 403 `forbidden_role` | — |
| 轮询 fs-request（GET，只读） | ✅ | ✅（沿用 GET 不限制角色，但仅能查自己发起的 id） | — |
| SSE 接收 fs_request | — | — | ✅（按 token 绑定 host） |
| ack/result 回传 | — | — | ✅（校验 host 归属） |

> 发起是 POST，严格沿用现有「非 GET 仅 admin + CSRF」中间件，不新增角色豁免。

## 9. 错误码总表

| code | 产生方 | 含义 |
|---|---|---|
| `forbidden_role` / `csrf_failed` | hub | console 权限/CSRF |
| `host_unknown` | hub | hostId 无 daemon 配置 |
| `host_offline` | hub | 目标 host 无 SSE 连接，未下发 |
| `path_not_allowed` | hub | 第一道白名单（会话 cwd）拒绝 |
| `invalid_request` | hub | 参数非法 |
| `not_found` | hub/daemon | requestId 已清理 / 路径不存在 |
| `denied` | daemon | 第二道白名单拒绝 |
| `denied_all` | daemon | `fsAllowedDirs=[]` 全禁 |
| `not_a_directory` / `not_a_file` | daemon | 类型不符 |
| `file_too_large` | daemon | 超类别大小上限 |
| `binary_unsupported` | daemon | 不支持的二进制类型 |
| `text_decode_failed` | daemon | 文本解码失败 |
| `expired` | hub | 60s TTL 到期 |
| `daemon_error` | daemon | 其它 fs 异常 |

## 10. 兼容性与迁移

- **新增能力，不破坏既有接口**：`/api/hub/sessions/:id/files` 等会话虚拟文件树接口保留（历史取证/无 daemon
  在线场景仍可用），本期仅把右栏默认数据源切换为真实目录。
- 协议包 `@pi-agent-hub/protocol` 新增 FS 请求相关 DTO 与 SSE 事件类型，不改既有类型字段。
